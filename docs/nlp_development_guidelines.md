# NLP 开发准则 — 行业规范与最佳实践

> 本文档记录了 narrative-operator-nlp 项目的开发准则，基于 NLP 领域的行业规范和最新标准。
> 所有新的功能和架构设计应参照本文档进行检验。

---

## 1. 实体抽取架构

### 1.1 三层抽取架构（行业标准）

| 层 | 方法 | 用途 | 控制方式 |
|---|---|---|---|
| **Layer 1** | 预训练 NER 模型 | 通用实体识别（PERSON/LOCATION/ORGANIZATION） | 始终运行 |
| **Layer 2** | 新词发现（统计方法） | 领域特定/未登录词发现 | 用户 opt-in |
| **Layer 3** | 自定义词典注入 | 领域专业知识 | 用户 opt-in |

### 1.2 开发准则

- **准则 1.1**: 实体抽取工具不应硬编码领域知识。领域知识应由调用方通过 API 注入。
- **准则 1.2**: 新词发现等召回率敏感的功能必须是 opt-in（默认关闭），让用户控制精确度/召回率权衡。
- **准则 1.3**: 避免使用简单的 POS-based 实体抽取作为独立层。POS 标签应作为辅助特征，不单独生成实体。
- **准则 1.4**: 实体类别 schema 应保持通用。如需领域特定类别，通过运行时注入而非硬编码。

## 2. 新词发现算法

### 2.1 算法要求（行业规范）

| 组件 | 要求 | 参考 |
|---|---|---|
| **PMI (互信息)** | 多分割点平均 PMI | Sun Maosong, HanLP 1.x |
| **LLR (对数似然比)** | 统计显著性检验 | Duan et al. |
| **左右分支熵** | 字符级邻接熵 | 行业标准 |
| **内聚度 (Cohesion)** | 内部结合强度，sigmoid 归一化 | 行业推荐 |
| **综合评分** | 加权组合，非单一指标 | 行业最佳实践 |

### 2.2 参数自适应（行业规范）

| 文本长度 | min_freq | min_score | n-gram范围 |
|---|---|---|---|
| 短文本 (<50字) | 1 | 0.3 | 2-6 |
| 中等文本 (50-200字) | default/2 | default*0.6 | 2-6 |
| 长文本 (>200字) | default (2) | default (0.5) | 2-6 |

### 2.3 开发准则

- **准则 2.1**: 新词发现必须使用多种统计检验（PMI + LLR + 熵 + 内聚度），而非单一指标。
- **准则 2.2**: 参数必须根据输入文本长度自适应调整，以支持短文本场景。
- **准则 2.3**: n-gram 范围应覆盖 2-6 字符，以捕获长复合词。
- **准则 2.4**: 必须进行子串过滤（subsume filter），避免短候选词被长候选词包含时重复报告。
- **准则 2.5**: 新词发现结果必须包含完整的统计指标（PMI、LLR、左右熵、内聚度），而非仅返回词串。

## 3. API 设计

### 3.1 领域知识注入（行业标准）

```
entity_categories: dict[str, list[str]]  # 运行时注入
auto_discover_entities: bool             # opt-in 开关
```

### 3.2 开发准则

- **准则 3.1**: API 必须支持运行时领域知识注入（entity_categories），而非硬编码。
- **准则 3.2**: 召回率敏感的功能（新词发现）必须通过布尔参数 opt-in，默认关闭。
- **准则 3.3**: API 参数应有清晰的文档说明，包括默认值、用途和影响。
- **准则 3.4**: 返回结果中的每个实体必须标注 source 字段（ner/discover/keyword），以区分来源。

## 4. 统计检验

### 4.1 行业标准的统计检验

| 检验 | 公式 | 用途 |
|---|---|---|
| **PMI** | log2(P(ab)/P(a)P(b)) | 共现显著性 |
| **LLR** | obs * log2(obs/exp) | 统计显著性 |
| **分支熵** | -Σ(p*log2(p)) | 边界清晰度 |
| **内聚度** | sigmoid(avg_pmi_of_splits) | 内部结合强度 |

### 4.2 开发准则

- **准则 4.1**: 统计检验必须使用对数底 2（log2），而非自然对数，以保持一致性。
- **准则 4.2**: 所有统计分数必须有合理的归一化或范围说明。
- **准则 4.3**: 综合评分应使用加权平均，权重之和为 1，便于解释。
- **准则 4.4**: 避免使用单一统计指标作为判断标准。

## 5. 架构设计原则

### 5.1 模块化设计

- **准则 5.1**: 每个组件（NER/POS/新词发现/关系抽取）应独立实现，通过编排器组合。
- **准则 5.2**: 配置与代码分离。领域关键词应存储在 YAML 配置文件中。
- **准则 5.3**: 核心算法（discoverer/mapper）不应直接依赖外部服务（HanLP），通过接口抽象。

### 5.2 数据流

```
文本输入 → 分词 → NER → 新词发现 → 自定义词典 → 合并 → 去重 → 排序 → 输出
```

- **准则 5.4**: 数据流必须是线性的，避免循环依赖。
- **准则 5.5**: 每层抽取的结果必须经过合并（merge）和去重（dedup）后才输出。

## 6. 测试要求

### 6.1 测试覆盖

- **准则 6.1**: 所有核心组件必须有单元测试。
- **准则 6.2**: 必须覆盖三种语言模式：现代汉语、古汉语、英语。
- **准则 6.3**: 必须测试边界情况：空文本、短文本、长文本、特殊字符。

### 6.2 集成测试

- **准则 6.4**: 必须有端到端集成测试，验证完整数据流。
- **准则 6.5**: 测试数据应包含真实场景样本，而非仅合成数据。

---

## 7. 性能与可扩展性

### 7.1 性能准则

- **准则 7.1**: 新词发现算法必须支持短文本（<50字），通过自适应参数调整。
- **准则 7.2**: 对于长文本，应限制候选词数量（max_candidates），避免内存溢出。
- **准则 7.3**: 统计计算应避免 O(n²) 复杂度，使用 Counter 等高效数据结构。

### 7.2 可扩展性准则

- **准则 7.4**: 新词发现算法应支持插件式扩展，允许用户添加自定义评分函数。
- **准则 7.5**: 实体类别 schema 应支持扩展，允许用户定义自定义类别。

---

## 8. 文档要求

- **准则 8.1**: 所有公共 API 必须有文档字符串（docstring），说明参数、返回值和异常。
- **准则 8.2**: 算法实现应引用相关学术论文或行业参考。
- **准则 8.3**: 配置文件的每个字段应有注释说明。

---

## 9. 版本与兼容性

- **准则 9.1**: 核心 API 应保持向后兼容。新增参数应有默认值。
- **准则 9.2**: 破坏性变更应记录在 changelog 中，并至少提前一个版本通知。
